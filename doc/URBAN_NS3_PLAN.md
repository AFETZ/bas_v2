# Городской сценарий BAS без обязательной Sionna

План от 28.10.2026; основание — аудит `964f7e27e494f7ae55890b2d4a71a6ebb9d848ee`.
Статус: **проектирование, не реализовано и не измерено**. Пользователь разрешает GPU, если он ускоряет работу; запрещать GPU не требуется. Сохранить ns-3, Gazebo/DART и пять настоящих ArduPilot SITL.

## 1. Решение и границы научного утверждения

Основной путь — отдельный профиль `geometry_logdistance`: геометрическая LOS/NLOS-классификация штатными `Building`/`BuildingsChannelConditionModel`, затем выбор штатного `LogDistancePropagationLossModel` с соответствующими параметрами. Разрешён тонкий адаптер выбора/логирования; собственные формулы распространения, PHY, MAC, PER и автопилот не нужны.

Это геометрически обусловленная **эмпирическая аппроксимация крупномасштабных потерь**, а не трассировка лучей и не измеренная радиокарта квартала. Геометрическое перекрытие меняет вход физической модели; исходы пакетов определяет native Wi-Fi. NLOS не обязан означать потерю связи.

Научный вопрос: при каких условиях доступный запасной бортовой ретранслятор повышает доступность управления и прогресс осмотровой миссии, а когда назначение избыточно либо невозможно? Вклад — воспроизводимая цепочка «геометрия → потери/пакеты → lease/UART → реальное движение», а не новая модель радио.

Без подходящих полевых данных параметры называются исследуемыми предположениями; выводы ограничиваются их зафиксированным диапазоном. Не заявлять материал стен, дифракцию, отражения, точность покрытия реального города или универсальный выигрыш failover. Калибровка по независимым измерениям — усиление, не выдуманная предпосылка.

| Компонент | Решение |
|---|---|
| Радиосеть | Существующие native ns-3 Wi-Fi PHY/MAC, ad-hoc и прямые peer routes |
| Здания | Штатные `Building` с 3D boxes; общие координаты с Gazebo collision/visual |
| LOS/NLOS | `BuildingsChannelConditionModel` по фактическим позициям антенн |
| Потери | LOS/NLOS-экземпляры upstream `LogDistancePropagationLossModel`; при обосновании отдельные параметры A2G/A2A |
| Полёт | Штатные Guided position setpoints, реальные SITL, последовательные безопасные waypoint-сегменты |
| Протокол | Существующие sole GCS issuer, probes, all-peer eligibility, epoch/lease, UART fence, BRAKE/Guided |
| Контроль | Новый горизонтальный LOS-only radio control с той же моделью; исторический Friis отдельно |
| GPU | Разрешён для готовых ускоряемых подсистем; эффект измерять. Основной канал не требует GPU/OptiX/Sionna |

## 2. Почему не просто другая готовая «городская» модель

`BuildingsChannelConditionModel` классифицирует LOS/NLOS, но сам не задаёт потери. `OhBuildings`/`HybridBuildings` не гарантируют учёт промежуточного корпуса для двух наружных узлов только по названию. Pinned UMi требует BS=10 м и UT<10 м; UMa — BS=25 м. Это не область произвольных A2A-пар на высотах 12–20 м. Нельзя выключить проверки диапазонов и назвать результат валидированным.

Существующий contrib FOBA/ONERA — полезный аналог, но не основной быстрый путь: проверенный public HEAD `b0359fc530ed20aea941fac3f7a1b66ecc4764eb` имеет возврат без зданий при base loss>90 dB, упрощённые XY-взаимодействия и фиксированную высоту отражения; документация не заявляет валидацию реальными измерениями. Исправление этого превращает этап в разработку радиомодели. INET/OMNeT++ потребовал бы замены уже проверенного сетевого тракта.

## 3. P0 — спецификация модели и единой сцены

1. Использовать один компактный идеализированный промышленный квартал из `reports/ispras/scenario/industrial_block_plan.json`; это не координаты Town01. Два корпуса достаточны. Если сохраняется Town01, явно импортировать реальные нужные объёмы и проверить совмещение; не рисовать дополнительные «невидимые радио-здания».
2. Единый scenario config содержит ENU datum/origin, здания, позиции/offset антенн, spawn, безопасные маршруты, скорости, высоты и общий горизонт наблюдения. Из него формируются Gazebo boxes и ns-3 Building objects. Проверить сегменты и торможение около углов, разнесение аппаратов, землю и крышу. Предложенные старые маршруты — исходный эскиз, не проверенная полётная миссия.
3. Сохранить фактическую частоту/полосу/мощность/MCS/антенны и RNG stream mapping. LogDistance не имеет Frequency-атрибута: задавать `Exponent`, `ReferenceDistance`, `ReferenceLoss` явно. Штатный default 46,6777 dB относится к 5,15 GHz; не переносить его на другую частоту. При free-space reference получить значение штатным Friis на фактической частоте и документировать метод.
4. Составить таблицу параметров LOS/NLOS отдельно для A2G и A2A: значение, источник, частота, высоты, расстояния, область применения. Не переносить A2G-измерения на A2A молча. Не выдумывать численные коэффициенты по одному abstract. Если переносимого набора нет, заранее объявить low/nominal/high как гипотезы чувствительности, без термина «калибровано».
5. Начать с детерминированных средних потерь. Не добавлять независимый случайный шум на каждый пакет под названием пространственного shadowing. Штатная случайность Wi-Fi сохраняется. Номинальные параметры и диапазоны нельзя выбирать по величине выигрыша failover.
6. Проверить конечность/взаимность потерь, рабочие расстояния, отсутствие NLOS-усиления относительно LOS в исследуемом диапазоне. Плохой набор отклонить до серии, а не исправлять собственной скрытой clamp-формулой.

Выход P0: небольшой `scenario`/`radio` config и таблица источников, список проверяемых предположений. Числа модели пока не выбраны этим планом — это обязательная задача до freeze.

## 4. P1 — native радио без тяжёлого runtime

1. Внести профиль в явные allowlists runner/C++; заменить проверки «всё кроме Friis требует RT» на явное перечисление RT-профилей. Новый профиль не импортирует/не инициализирует Sionna и не запускает GPU/OptiX preflight. Старые профили сохраняются. Установленные неиспользуемые пакеты pinned image не требуют немедленной пересборки образа.
2. Подключить тонкий LOS/NLOS selector через `MultiModelSpectrumChannel::AddPropagationLossModel`. Он делегирует вычисление upstream-модели и не решает судьбу пакета.
3. В этом профиле **не подключать одновременно** существующий FriisSpectrum/SourcePropagation: scalar pathloss уже меняет принимаемую PSD. Нельзя дважды учитывать свободнопространственные потери. Effective-config должен показывать реальную цепочку.
4. Передавать актуальные реальные poses через existing mobility adapter, установить/обновлять `MobilityBuildingInfo`. Земля/антенны/ENU должны совпадать между физикой и радио. Не подменять позы маршрутом из config.
5. Использовать 3D-проверки всех 15 неупорядоченных пар шести узлов; доставку логировать по направлениям. Геометрию вычислять при обращении модели; отдельный диагностический sampler допустим. Не начинать с GPU/offline-карт/кэшей: сначала измерить стоимость. При необходимом кэше зафиксировать предел давности и ошибку положения; не пропускать переходы за угол.
6. Минимальные model probes: LOS; пересечение одного корпуса; очистка над крышей; перемещение препятствия при тех же узлах; смена порядка узлов; два корпуса; обходной путь; одинаковые LOS/NLOS-параметры как отрицательный контроль. Проверить и числа потерь, и реальные native пакеты, без SITL на этом шаге.

Выход P1: воспроизводимые команды probes, CSV actual poses/LOS/loss/packet outcomes, подтверждённое отсутствие двойного pathloss и RT runtime. Это квалификация реализации, не полевая валидация модели.

## 5. P2 — безопасное горизонтальное исполнение

1. Отдельный scenario mode в существующем mission driver. Использовать upstream MAVLink Guided position commands; сверить ENU→NED/EKF origin каждого борта или ENU→global/home через готовые координатные средства. Проверить движение вдоль +X/+Y и изменение Z на одном аппарате, затем на пяти.
2. Разделить refresh текущей цели и переход к следующему waypoint. Нельзя перескакивать угол по таймеру: после обрыва новая дальняя цель может провести аппарат сквозь корпус. Следующий безопасный сегмент активируется по свежей телеметрии SITL, реально полученной НПУ через ns-3. Недоступная телеметрия означает ожидание.
3. Ground truth Gazebo используется для сетевой физики и независимого офлайн-анализа, но не как скрытый канал продвижения миссии/выбора relay. Не предзагружать автономную миссию, которая продолжает полёт вопреки экспериментальному BRAKE.
4. Переиспользовать `RegionHold`: там уже есть XY/Z tolerance, speed и dwell. Дополнить регистрацию реального горизонтального/3D displacement, траектории и waypoint identity; старый `maneuver_observed = max_vertical_displacement >= 1` не годится для горизонтальной миссии. Не переписывать работающий dwell без необходимости.
5. Предварительные критерии: XY≤3 м, |Z error|≤1,5 м, speed≤1 м/с, dwell≥2 модельных секунд на неповторяющихся poses; разрывы >0,5 с сбрасывают dwell. Для контрольных движений назначать точки с ожидаемым горизонтальным перемещением ≥5 м и проверять фактическое перемещение. Сохранить источники, clock domains и lineage goal/CID/epoch. Эти допуски — инженерные критерии, не авиационная норма и не «строго неподвижен».
6. Завершить пилот: все пять реально взлетают, горизонтально идут по безопасным сегментам, меняют высоту, удерживаются, LAND/disarm по доступному штатному пути. Изменение высоты должно влиять на 3D LOS, а не только украшать график.

## 6. P3 — один содержательный сценарий

НПУ с юго-запада квартала; UAV1 — исходный relay, группа осматривает корпуса; UAV1 и ещё один борт уходят за угол. UAV3 проходит западный коридор, потенциально сохраняя CP→UAV3 и UAV3→остальные. Все пять имеют горизонтальные сегменты; высоты разнесены. Существующий эскиз: GCS[0,0,2], корпуса A=[40..70,20..65,0..30], B=[95..125,20..65,0..25]. Все числа требуют проверки геометрии и полёта P0–P2.

Проверять граф **всех** каналов: нынешний кандидат обязан иметь свежую связь с НПУ и peer-подтверждения ко всем четырём остальным, включая прежний relay. Геометрически удобный UAV3 ещё не означает допустимого кандидата. Выбор не подсказывается сценарием и не использует недоступные НПУ LOS/ground-truth данные.

Основная городская серия не использует Matrix=200 dB, iptables DROP и ручное выключение канала. Причина потерь — actual geometry и объявленная модель. Если параметры не приводят к отказу, сохранить результат; не докручивать их после просмотра эффекта политики.

Fixed может остановиться за зданием в BRAKE до конца окна. Это результат, а не причина двигать его снаружи. До пилота определить остановку по горизонту и отдельную явно залогированную лабораторную очистку после окна. Аварийное вмешательство не засчитывается как восстановление либо штатное завершение миссии; не удалять здания в измерительном окне.

## 7. P4 — freeze, контроль и статистика

После пилотов, до первого основного опыта, сохранить commit/image, configs, исходные состояния, seeds/streams, порядок, число попыток, clocks, горизонт наблюдения, endpoints, правила пропусков и план анализа. Первая рекомендация — 300 модельных секунд наблюдения; принять окончательное значение по длине безопасной миссии и стоимости пилота, не по эффекту failover. Пилоты анализировать отдельно.

| Серия | Дизайн | Объём до запуска |
|---|---|---|
| Основная | fixed/failover × geometric NLOS / radio LOS-only × 10 парных повторов на радиорежим | 40 запусков |
| Чувствительность | low/high NLOS-параметры, та же геометрия × fixed/failover × 3 пары | 12 запусков; разведочная |
| Границы | краткое геометрическое перекрытие; отсутствие допустимого кандидата — по одной паре | 4 инженерных запуска |

Если измеренный бюджет не позволяет 56 запусков, **до freeze** сократить основную часть до пяти пар на радиорежим: всего 36. Тогда интервалы явно разведочные. Десять пар также не гарантируют статистическую мощность. Не останавливать и не продлевать серию по значимости. Старую матрицу искусственных отказов не повторять.

LOS-only — объявленная радиo-абляция: физические корпуса/маршруты остаются, selector использует LOS-параметры для всех связей, геометрический NLOS всё равно записывается. Это отделяет влияние параметризации препятствий от расстояния/движения; сравнение только с историческим Friis этого не делает.

Организовать основную часть в 10 (либо заранее выбранные 5) независимых блоков по четыре запуска: `(fixed/failover) × (geometry/LOS-only)`, общие исходные условия и seed внутри блока, случайный заранее сохранённый порядок. Внутри пары одинаковы старт, план миссии, настройки, seed/stream mapping и расписание возможностей обновления текущего безопасного setpoint. После отказа actual траектории/экспозиция расходятся как часть эффекта управления — не выравнивать их искусственно. Один seed не гарантирует одинаковую последовательность случайных исходов при разных событиях.

Основная статистическая единица — независимый запуск/пара, не пакеты, UAV или NLOS-эпизоды. Сравнивать парные разности на общем горизонте, показывать все точки и интервалы по целым парам. Для абляции дополнительно разность эффектов failover между NLOS и LOS-only. При валидном невосстановлении до административного конца окна — recovered/N и правое цензурирование; по возможности survival/RMST при фиксированном горизонте. Crash runtime/потеря журнала — отдельные failed attempts, а не автоматически независимое цензурирование: показать долю, причины, миссионный исход и влияние пропусков. Не усреднять только успешные восстановления без явной оговорки.

## 8. Метрики и первичные данные

- Доступность: scheduled opportunity→offered→CID creation→оба радио-перехода→follower receive→UART write-end. Timely deadline=250 мс от command.created до UART, offered — знаменатель. Дополнительно opportunity-to-UART выявляет задержку до создания команды. После достижения финальной точки продолжать объявленные refresh удержания до общего горизонта; отделять их от прогресса миссии.
- Задача: достигнутые уникальные waypoint IDs / все запланированные точки, длина/доля пройденного маршрута, простой, завершение всей миссии. Частые команды удержания не равны осмотру новых точек.
- Геометрия: фактические t_NLOS/t_LOS, blocked link/building IDs, antenna poses/datum, loss и используемый parameter-set, model/host clock mapping. Потеря пакета не доказывает NLOS; NLOS не доказывает потерю.
- Восстановление: общий trigger — первый после начала окна переход CP↔исходный UAV1 из LOS в NLOS по фактической геометрии. По каждому UAV и всей группе измерять время до UART свежего target-bearing CID, созданного после trigger; отдельно события наблюдаемой деградации, detection, selection, issued/valid_from/activation, receive, write-end. Если доставка не ухудшалась, это latency первого обновления после NLOS, а не восстановление отказа. Нет самого trigger — N/A, а не цензурированное восстановление. Для handover-specific endpoint дополнительно требовать новый relay/epoch; в control без handover это N/A. Не суммировать стадии без проверки их порядка для одной lineage.
- Физика: новый `T_inspection_resume` — наблюдаемое завершение ранее недостигнутой осмотровой точки после подходящего post-event UART. Цель могла быть создана/допущена раньше события, поэтому последующий refresh не доказывает, что именно он вызвал движение. Для утверждения «возобновилось после HOLD» отдельно подтвердить BRAKE→Guided и actual движение. Исторический T_goal с «новой после отказа целью» считать отдельно; указывать выбранную цель, время создания/ожидания/доставки/движения и selection bias первого успешного результата.
- Заранее назначить контрольные waypoint IDs после угла и показать достижение к общему горизонту; это уменьшает зависимость вывода от выбора «первой удобной достигнутой» цели.
- После фактического выхода из NLOS: доля UART-admitted/offered в заранее зафиксированном окне, например 5 с. Нет выхода — endpoint N/A; невосстановление за горизонт цензурировано. Не исключать такие запуски.
- Полномочия: все выданные интервалы/grants, 0 конфликтующих lease, 0 устаревших/повторных допусков; причины недопустимости каждого кандидата; число назначений и случаи активации после восстановления старого канала. «Лишнее назначение» определить до серии, не по субъективной картинке.
- Производительность: RTF по окнам, p95/max lag/pose age, CPU/RAM, GPU util/VRAM при использовании, стоимость radio computation, пропуски логов. Отсутствующее измерение остаётся отсутствующим.

## 9. Производительность, GPU и готовность к серии

Сначала короткий CPU radio probe, затем один headless live-пилот. Для шести узлов/двух корпусов GPU-перенос геометрии заранее не обоснован. Если profiler показывает проблему, использовать готовое ускорение конкретной подсистемы; сравнить end-to-end wall time/RTF/lag и неизменность смысла модели. GPU разрешён для визуализации и поддерживаемых вычислений, но не считать само наличие видеокарты ускорением DART или ns-3. GUI измеряется отдельным окном; full-stack builds/runs остаются последовательными.

Принять прежние live-ориентиры: RTF 0,98–1,02, p5 одноcекундных окон≥0,95; не ослаблять lag250 мс/pose age500 мс/source skew100 мс. Показать реальные распределения. Если live нарушен, упрощать визуализацию/логирование лишнего/геометрию, не замедлять часы lease и не подменять полёт. Успех в заданном RTF пока не измерен.

Серия начинается после: model probes; реального XY/Z цикла пяти; подтверждённого routing через relay; одной fixed/failover пилотной пары с geometry radio; независимой проверки логов/метрик; frozen конфигурации. Отсутствие пользы failover само по себе не блокирует серию, если измерительный тракт корректен.
