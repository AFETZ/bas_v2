# BAS: live-стенд и смена координатора для статьи

Дата: 26.10.2026. Это план реализации, а не отчёт об успешных испытаниях.

## Результат и границы

Пять настоящих ArduPilot SITL в Gazebo на `rock_demo` (основная карта) или Town01, управляемые через native ns-3, работают в реальном времени. НПУ отправляет задание одному координатору, тот распределяет задания четырём остальным. После избирательной потери связи НПУ с координатором НПУ назначает другого доступного аппарата. Сохраняются конфигурации, траектории, доставка и исполнение заданий; автоматически строится понятный отчёт и графики для статьи.

Обязателен live; ускоренный headless batch — последующее расширение. Ручное управление проверяется в live. Не обещаем одновременно ускоренный ход модели и обычные настенные сроки оператора. Sionna опциональна. Friis не учитывает затенение зданиями и рельефом: карта остаётся физической/визуальной средой, а сетевые отказы в основной статье задаются явно.

«Мастер» здесь — координатор задания и прикладной ретранслятор, назначаемый НПУ. Это не распределённый консенсус и не новый регулятор полёта. НПУ остаётся единственным источником назначений. При потере НПУ со всеми аппаратами новое назначение невозможно; аппараты переходят в заранее выбранное штатное удержание/failsafe.

## Архитектура с переиспользованием

Использовать Gazebo + штатную модель/плагины ArduPilot + пять SITL; существующий tracker; native ns-3 Wi-Fi PHY/MAC; `FriisSpectrumPropagationLossModel`; существующие UART/TAP adapters и MAVProxy. Настройки и версии закрепить. Не писать собственные MAC, PER, ACK, динамику, моторный контроллер или формулу распространения.

Для опыта координатора добавить явно выбираемый `AdhocWifiMac` и on-link peer адресацию. BSS сохранить как отдельный baseline. Проверить совместимость TAP/UseLocal и native MAC. Смена MAC без устранения маршрута peer→GCS→peer не считается решением.

НПУ → native radio → sidecar координатора → native radio → sidecar follower → настоящий UART SITL. Ответы возвращаются через координатора. Координатор исполняет свою часть задания локально; остальные четыре получают индивидуальные позиции/высоты через него. Простая последовательность Guided/AUTO setpoints с разными offsets достаточна. ArduPilot Follow — необязательное развитие после проверки версии `FOLL_SYSID`, не новый flocking-код.

Служебные heartbeat, probes, назначения и продления разрешены от НПУ кандидатам по тому же native радио. Их трафик измеряется отдельно. Исполняемые задания по служебному пути не обходят координатора. Local diagnostics могут читать состояние для записи, но решения НПУ принимаются только по доступным ей сетевым сообщениям.

В обычном операторском профиле можно выбирать каждый борт. В relay-профиле команды оператора проходят через dispatcher выбранного координатора. Любой отдельный аварийный канал явно отделяется и не используется в оценке восстановления.

## Минимальная прикладная политика смены координатора

Новая авторская часть ограничивается role/lease/dispatcher adapter; native транспорт и автопилот выполняют свою работу. Конверт содержит `run_id`, `epoch`, `leader_id`, `sequence`, `valid_from`, `valid_until`, адрес назначения и исходную полезную нагрузку. Перед записью в UART повторно проверяются полномочия, срок и дедупликация; очередь старого epoch очищается/отбрасывается. Полностью записанную ранее команду нельзя объявить отменённой только по удалению записи из очереди.

Начальные значения пилота: heartbeat 5 Hz, detection timeout 1 s, lease 2 s, renewal каждые 0,5 s. Выбор нового кандидата — по полученным heartbeat/RTT; детерминированный SYSID tie-break. Доступность кандидата и всех follower проверяется сообщениями, а не чтением глобального состояния. Не обещаем оптимального выбора.

Epoch сам по себе не исключает одновременные полномочия у разных follower. НПУ учитывает максимальный срок ВСЕХ выданных старому master lease, включая неподтверждённые продления. Новый lease активируется после этого срока с запасом рассогласования или после подтверждённого отзыва у всех исполнителей. В live на одном kernel разрешена общая host-monotonic шкала; её область применимости указать. Не переносить гарантию на физически распределённые машины без отдельного механизма синхронизации.

Позднее старое продление не должно продлевать власть после нового назначения. Просроченное новое назначение не активируется. Недоступные follower не считаются успешно переключёнными. По expiry штатное удержание должно реально отменить/приостановить прежнее движение; сам факт потери sidecar lease не останавливает AUTO-миссию. Описать сбой sidecar отдельно: для MVP остановка процесса делает запуск неуспешным, если штатный автопилотный failsafe не обеспечивает объявленное поведение.

При selective GCS↔UAV1 loss прежний master входит в четвёрку follower только при живом UAV1↔UAV2 link. Если радио UAV1 выключено целиком, доступны лишь три follower. Полная изоляция НПУ — отрицательный контроль, не повод имитировать выбор нового master. Автоматический failback в первом эксперименте выключен.

## Введение отказов

Для воспроизводимого RF fault injection использовать штатную `MatrixPropagationLossModel` как явно объявленную дополнительную потерю выбранной пары поверх базового Friis; для остальных пар добавка 0 dB. Проверить отсутствие двойного учёта базовых потерь и реальный эффект в native PHY. Выбрать величину по отдельному пилоту, затем заморозить. Это синтетическое воздействие, не доказательство затенения зданием.

Допустим вариант native link/filter fault injection, если он быстрее: тогда называть воздействие отказом сетевой доставки и измерять нужные направления. Нельзя незаметно менять исходы только в отчёте/ACK-адаптере. Полное выключение PHY используем как отдельный отрицательный контроль. Время фактического включения/снятия отказа записывается.

## Логирование и продуктовые результаты

«Все параметры» = все эффективные настройки использованных компонентов + объявленный набор динамических измерений + изменения настроек в ходе опыта. Не обещать запись каждой внутренней переменной движков.

Обязательный снимок: world/SDF и параметры физики; ArduPilot params/версия/модель; ROS topics/QoS/frames; ns-3 topology/PHY/MAC/propagation/queues/fault schedule; scene/config copies; source revision и фактические локальные изменения; seeds/RngRun; временной режим; профили логирования; аппаратная конфигурация. Неподдерживаемый экспорт помечается `not_supported`, выключенный — `not_enabled`, измеренный — `observed`.

Live: события заданий/ролей/отказов сохраняются все; позиции для графиков 10–20 Hz при неизменной частоте tracker/управления; health/resources 1–2 Hz; счётчики сети; необходимые ограниченные PCAP. Камеры, lidar, dense PHY debug и полная запись видео выключены, если задача их не использует. Запись пакетируется, ошибки и пропуски записи видны. Нельзя ускорять симуляцию удалением необходимых управляющих сообщений.

Diagnostic: те же обязательные события + batched PHY/MAC/queue traces, подробный PCAP, выбранные ROS topics, штатные DataFlash/tlog. Проверить реальное сохранение этих файлов, не только наличие включённого флага. `rosbag2`/MCAP — опциональные штатные средства, без обязательного `record -a`. Onboard лог и наблюдаемая с НПУ телеметрия сохраняют разную видимость при обрыве связи.

Расширить существующий Matplotlib report; не вводить обязательную БД/веб-сервис. Для интерактивного просмотра использовать совместимую установленную PlotJuggler при наличии. Основные графики строятся offline из raw, не нагружают горячий цикл.

Высота подписывается как world ENU z или `z−z_takeoff`; это не AGL. Для AGL нужна высота рельефа под каждым UAV. AMSL/MAVLink-relative-alt показывать отдельно. Временная ось траекторий — `source_sim_time_s`; настенное время и время сети не смешиваются. Пропуски — разрывы/null, не нули и не дорисованная траектория.

Графики: пять actual/target высот; XY/3D траектории; текущий master/epoch; fault→detect→grant→activate→первое полезное исполнение у каждого follower; latency CDF вместе с потерями; PDR/своевременные задания по получателям; RTF/lag/pose age/CPU/RAM/log bytes.

## Последовательность реализации

### P0. Зафиксировать исходное состояние — до 2 часов

Проверить подготовленные worktrees и snapshot. Назначить владельцев файлов и runtime. Получить один существующий Friis stationary run. Не выполнять полную новую матрицу до рабочего полёта. Проверить доступность pinned контейнера, private ns-3 build и rock assets.

### P1. Один аппарат, затем пять в live — главный критический путь, 0,5–1,5 дня

Сделать preflight/инициализацию profile-aware. Воспроизвести отсутствие подъёма одним SITL; сопоставить модель, моторные плагины, physics engine, sensor frames и параметры с upstream. Не отключать все arming checks. Диагностический прямой upstream опыт допустим только для локализации, итоговый путь проходит ns-3. Подтвердить физический цикл 1 UAV, затем 5. Измерить headless; включить GUI отдельным измеренным повтором.

### P2. Наблюдаемость — параллельно P1, затем интеграция

На существующих raw добавить CSV и график высот пяти аппаратов, затем effective config snapshot и событийный интерфейс handover. Согласовать поля до написания dispatcher. Общие runner hooks интегрирует владелец runtime. Оценить стоимость GUI off/on × live/diagnostic в четырёх коротких пилотах; для утверждений о стоимости — минимум три парных повтора.

### P3. Независимая peer-связь и настоящее relay — 0,5–1 день после P1

Добавить native ad-hoc profile, проверить routes/TAP. Сначала одно сообщение через два радио-перехода и реальный ответ SITL. Остановить forwarding master: задания больше не доходят, остальные процессы работают. Затем пять UAV, один master и четыре follower; повторить с другим master без отказа. Не начинать election на неверной топологии.

### P4. Смена master — 0,5–1 день

Добавить тонкую lease/epoch политику, delayed/reordered grants, одностороннюю потерю, просроченные очереди и total-GCS-loss. Сначала focused protocol tests с управляемыми часами; затем настоящий радио/SITL опыт. Unit tests не заменяют integrated result. Показать восстановление принятия задания и движения всех достижимых follower.

### P5. Эксперимент и статья — 1 день после стабильного P4

Две политики (фиксированный master / переключение НПУ) × три условия (без отказа / selective GCS-master loss / полная изоляция НПУ) × пять парных повторов = 30 запусков. Цель — десять повторов, если позволяет машина; не выдавать пакеты за независимые повторы. При смене snapshot или настроек затронутые сравнения повторяются. Все failed runs сохраняются.

Baseline отличается только запретом выбора другого master: транспорт, lease/expiry, HOLD, нагрузка и логирование одинаковы. После возвращения связи fixed-master вправе возобновить работу через прежний аппарат с действующими полномочиями. Не делать baseline искусственно неспособным восстановиться.

Основная серия 180 model s после готовности: 0–45 normal, 45–105 fault, 105–180 recovery. В no-fault интервалы те же. Миссия и семена парные, порядок политик рандомизирован, без параллельного GPU/runtime. Основной профиль, карта, нагрузка, интервалы heartbeat/lease и пороги замораживаются после пилота. До масштабирования измерить фактическую цену одного запуска.

До 31 октября план плотный. Если P1 не готов к концу первого рабочего дня, приоритет — live/полёт/логи, затем минимальное relay и selective loss; ускоренный batch, вторая карта и Sionna снимаются с критического пути. Если не готов настоящий relay/failover, не подавать статью с утверждением об их реализации; сузить публикацию до фактически апробированного стенда.

### P6. Ускоренный batch — только после обязательного результата

Согласовать Gazebo, SITL, ns-3, sidecar deadlines и leases по модельному времени; одинаковая скорость на всех участниках. Цель RTF>1 измеряется end-to-end. Сравнить модельные метрики live и batch на одинаковом задании. Изменение одного `SIM_SPEEDUP` не считается ускоренной системой. Ручной live режим сохраняется отдельно.

## Метрики и публикационный вывод

Общий для обеих политик показатель восстановления управления — время от фактического fault_start до подтверждённого UART admission задания, созданного НПУ после отказа и переданного разрешённым данной политикой master под действующим epoch, отдельно по UAV и по всей группе. Для fixed-master допустим прежний master после возвращения связи. Для подтверждения именно handover у failover дополнительно требуются другой master и новый epoch; к этому событию относится проектная цель ≤4 s, а не к завершению движения. No-fault оценивает стоимость и доступность; время восстановления после несуществовавшего отказа ему не приписывается.

Отдельный продуктовый показатель — перерыв полезного исполнения: от последнего завершённого до отказа задания до завершения первого подходящего нового задания. Зафиксировать одинаковую частоту заданий и критерий достижения/удержания, чтобы не смешивать эффект политики с миссией. Завершение старой команды после отказа не засчитывается как успех нового координатора. При отсутствии соответствующего события — цензурирование на конце окна. Сопоставлять также своевременность заданий всем пяти аппаратам, а роли и четыре relay-получателя показывать отдельно, чтобы смена состава follower не скрыла недоступный UAV. Дополнительно detection/selection/activation times, delivery/execution по всем отправкам, duplicate/stale UART admissions, actual/target altitude error, минимальное разделение, RTF и overhead.

Для команды различать `received_by_sidecar`, `written_to_UART`, `ACK_accepted`, `observed_action_completed`. Для движения критерий завершения — достигнута заданная область и удержана заданное время; допуски зависят от выбранной миссии, фиксируются до серии. ACK не равен выполнению. Логи ground truth применяются для анализа, но не дают НПУ тайных знаний при выборе.

Сравнивать парные показатели запусков; показывать все точки, оценку эффекта и 95% интервал по запускам, не по пакетам. Для группового успеха нужны все заявленные достижимые исполнители. Fairness сама по себе не означает доставку. No-fault — overhead baseline, total-GCS-loss — отрицательный контроль. Не обещать улучшение до получения данных.

Рабочее название статьи: «Программно-имитационный стенд для исследования восстановления управления группой БПЛА при смене координатора связи». Вклад: работающий сквозной стенд, воспроизводимая постановка и измеренные ограничения известной политики переключения. Не заявлять новый consensus, геометрически точное радио с Friis, физический HitL или гарантии hard real time.

## Мультиагентная работа

Максимум основной интегратор + три активных помощника. Фазы: runtime/relay/metrics параллельно на независимых участках; затем experiments/reviewer. Каждый агент читает свой skill, AGENTS и только относящиеся исходники. Новую иерархию агентов не создавать без пользы.

| Роль | Skill | Рабочая копия / владение |
|---|---|---|
| Интегратор | bas-orchestrate | `/home/bas/bas_v2-paper-live`; shared entrypoints, интерфейсы, интеграция, full runs |
| Runtime/topology | bas-live-runtime | `/home/bas/bas_v2-paper-runtime`; Gazebo/SITL, ns-3 scratch, runner/preflight. Только этот worker пишет общий C++/shell, root интегрирует последовательно. |
| Relay | bas-relay-handover | `/home/bas/bas_v2-paper-relay`; новый узкий coordination module/config/tests. Изменения общего runner запрашивает у владельца. |
| Metrics | bas-metrics | `/home/bas/bas_v2-paper-metrics`; exporter/report/plots и их focused tests; не меняет исходы пакетов/ролей. |
| Experiments | bas-experiments | Читает интегрированную версию, подготавливает серию и анализ; тяжёлые запуски только с runtime slot. |
| Reviewer | bas-review | Независимое чтение diff/raw; проверка обходов, lease и статистики, без правок чужих файлов. |

Разные worktrees не изолируют порты/netns/GPU/изменяемый ns-3 build. Все full-stack и native builds идут из интеграционной копии по одному, под `flock --nonblock --conflict-exit-code 75 /tmp/bas-paper-runtime.lock <command>`. Нельзя останавливать чужой запуск. Workers выполняют только лёгкие независимые проверки, heavy result получают после интеграции.

Не symlink-share writable `.external`, build/install. Интегратор использует частную копию pinned ns-3; неизменяемые assets допускают read-only доступ. Один commit = одна законченная продуктовая задача; inherited snapshot явно помечен как непроверенный. Root сохраняет только короткий итоговый update `network/STATUS.md`; вспомогательные PASS-системы не создаются.
