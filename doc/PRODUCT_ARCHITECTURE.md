# Архитектура RC1

Основной путь: `MAVProxy/сценарий → BSF1 → GCS TAP → native Wi-Fi AP/STA →
UAV TAP → BSF1 → настоящий UART ArduPilot`. Обратные ACK и телеметрия идут
тем же путём. У каждого SITL свои control/payload UART, SYSID и ROS odometry.
Payload UART является вторым MAVLink UART, не видео.

## Связи симуляторов и владение состоянием

В активном тракте четыре симулятора. ROS 2/ros_gz — транспорт состояния,
MAVProxy — операторский клиент. CARLA здесь не запущена: используются внешние
ресурсы сцены. Матрица покрывает все шесть пар активных симуляторов.

| Пара | Прямая связь и необходимое обратное влияние |
| --- | --- |
| Gazebo ↔ ArduPilot SITL | ArduPilotPlugin: физические датчики/FDM → SITL, моторные команды → Gazebo; штатный lock_step. Gazebo владеет истинным движением, SITL — управлением и оценкой состояния. |
| Gazebo → ns-3 | ros_gz Odometry + Clock → tracker → атомарный снимок → MeasuredMobility. ENU XYZ, скорость, quaternion, исходное время. Обратное влияние через доставку команд в SITL и моторы. |
| Gazebo → Sionna | Через MeasuredMobility в ns-3: координаты, скорость для Doppler, yaw/pitch/roll для антенны. Прямого физического перемещения от радиомодели нет. |
| ArduPilot ↔ ns-3 | Настоящие MAVLink-байты SERIAL1/2 ↔ PTY/BSF1 ↔ TAP ↔ штатные Wi-Fi PHY/MAC/очереди. Потери влияют на полученные команды/телеметрию и штатные реакции SITL. |
| ns-3 ↔ Sionna | In-process upstream API: состояние концов/антенн/частота → RT paths/канал → received PSD. Решение о приёме, MAC ACK и повторах остаётся у ns-3. |
| ArduPilot ↔ Sionna | Косвенная замкнутая связь: управление → движение Gazebo → канал; канал → доставка ns-3 → SITL. Прямой API команд между ними не нужен. |

Изменять движение нужно в Gazebo либо командой автопилоту. Изменять координаты
только в ns-3 означало бы рассогласовать физику. Оценка позиции EKF может
отличаться от ground truth; это не повод переписывать состояние Gazebo.
Результаты RT не подменяют состояние полёта и не создают MAVLink ACK.

Gazebo моделирует движение и коллизии. ArduPilot исполняет команды и автономную
миссию. Position tracker атомарно передаёт настоящую одометрию в MobilityModel.
`SionnaRtSpectrumPropagationLossModel` рассчитывает received PSD. Стандартные
SpectrumWifiPhy, NistErrorRateModel, Wi-Fi association, MAC/ARQ, QoS queues и
конкуренция за эфир ns-3 определяют приём. JSON используется для входов/журналов,
а custom JSON/PER provider не участвует в этом тракте.

## Общая радиосеть

Одна BSS: НПУ — AP, БАС — STA. Межбортовой P2P проходит реальные штатные BSS hops.
P2MP создаёт один application multicast root; каждый получатель фиксирует свою
уникальную доставку. Это не пять application unicast sends; multicast не имеет
выдуманного MAC ACK. Одновременный uplink использует тот же эфир.

IEEE 802.11n reference: 2412 MHz, channel 1, 20 MHz, 10 dBm, HtMcs0,
control/basic ErpOfdmRate6Mbps, один изотропный элемент. Калибровки изделия нет.
Конфигурация: `network/config/native_wifi_80211n_spectrum_product.yaml`.

## Источники и альтернативное распространение

`native-spectrum-sources.h` только связывает WaveformGenerator/антенну/позицию
с public phased-array API. Перед каждой передачей выбирается ровно одна native
propagation model; потери двух моделей не складываются. Параметры источника:
position, orientation, frequency/bandwidth, rectangular PSD, feed gain, power,
iso/tr38901 antenna, start/stop, period/duty, continuous/pulsed/sweep.
Частотные сегменты имеют отдельные модели нужной частоты. События излучения
планирует ns-3; TTL геометрии не откладывает включение или перестройку.

По умолчанию всегда Sionna, без fallback при ошибке. Явный
`BAS_NATIVE_PROPAGATION_PROFILE=friis` выбирает штатный FriisSpectrumPropagationLossModel.
`hybrid` применяет Friis только когда оба конца имеют x>2000 m и z≥200 m,
а расстояние ≥500 m; остальные links использует Sionna. Это инженерное правило
для открытой высокой трассы вне Town01, не автоматический детектор LOS.
Для Friis разрешены только изотропные элементы. Экранирование холмами, городской
клаттер, направленные антенны и наземные трассы этим простым профилем не подтверждены.
Возле границы возможен скачок между моделями. В статистике выбор записан явно.

## Время и отказ

Gazebo RTF=1; ns-3 RealtimeSimulatorImpl работает по wall clock. Модельное время
ns-3, ROS/Gazebo и host monotonic хранятся раздельно. RTT — разность host monotonic.
Синхронный RT solve может задержать обработку; p95 не ограничивает редкий максимум.
Выбран режим реального времени с остановкой при нарушении сроков. После готовности
BSS включается штатный ns-3 HardLimit: отставание более 250 ms завершает процесс.
До готовности допускается прогрев Sionna; UART закрыт до здорового heartbeat.
Свежие публикации при замедленной физике недостаточны: относительное расхождение
часов Gazebo/ns-3 после готовности также ограничено 500 ms.

Tracker сохраняет source timestamp, host receive time и оценку host sample time,
которая учитывает отставание сообщения от последнего Clock. Это измерение на
границе ROS, не доказательство точной задержки до ROS. QoS KEEP_LAST(1), BEST_EFFORT
не накапливает старую одометрию; локальная история ограничена 32 измерениями на UAV.
Скорости из child_frame поворачиваются в мировой ENU по quaternion, как требует
[ROS Odometry](https://github.com/ros2/common_interfaces/blob/humble/nav_msgs/msg/Odometry.msg).
Такой body-frame twist действительно публикует
[Gazebo OdometryPublisher](https://github.com/gazebosim/gz-sim/blob/gz-sim8/src/systems/odometry_publisher/OdometryPublisher.cc).

Каждые 20 ms ns-3 выбирает последнее измерение не позднее времени события.
Применяются сразу все узлы; при неполном снимке частичного обновления нет.
Возраст измерений/Clock ограничен 500 ms, межбортовой skew исходного времени —
100 ms. Отсутствие узла, NaN, неверный frame, смена tracker session, остановка
или сброс часов после готовности прекращают запуск. Экстраполяции движения нет.
Сброс мира требует перезапуска всего запуска.

Кэш обоих product-профилей теперь ограничен 0.5 s/0.5 m, jitter .5 сокращает эти
пороги для разных пар. Изменение скорости на 0.5 m/s или любого угла на 5° также
инвалидирует канал. Пересчёт выполняется при следующем запросе канала. Это
явная дискретная аппроксимация, не мгновенный пересчёт каждого физического шага.
Старый профиль 20 s/10 m и его измерения не подтверждают производительность нового.
При превышении max_number_of_paths расчёт завершается ошибкой: глубина solver
автоматически не уменьшается. Ошибки не включают другую модель распространения.

Heartbeat обновляется каждые 50 ms модельного времени и содержит monotonic stamp
и признак здоровья. Оба UART gateway закрывают обмен через 300 ms без обновления.
В пятибортовом runner горячие снимки/heartbeat находятся в Linux /tmp, итоговый
снимок сохраняется в журнал. Host monotonic предполагает общий Linux kernel;
разнос симуляторов по нескольким компьютерам потребует отдельной синхронизации.

Очереди UART ограничены 128 записями/64 KiB на направление. Control deadline —
250 ms, payload — 1000 ms от исходного ingress, включая сеть, reassembly и запись.
Частичная запись сохраняет исходный срок; неблокирующий цикл продолжает watchdog
и очистку очереди. Ожидание потерянной записи ограничено половиной deadline.
Переполнение/просрочка учитываются как потери. Проверяются IP и порт отправителя.
Это сроки адаптеров, а не гарантия доставки и не hard-RT гарантия ОС.

## Внешний контроллер и НПУ

`external_endpoint.py` использует тот же BSF1. Serial 8N1, UDP и TCP client имеют
ограниченные очереди/реассемблирование, deadline, reconnect и watchdog.
Radio socket создаётся в ams-uav1, внешний Ethernet socket — в host namespace;
дополнительный сетевой маршрут между НПУ и FC не создаётся. Serial подключается
через конфигурацию. Это эмулятор приёмопередатчика, не flight-HIL с датчиками.

`native_operator_bridge.py` раскрывает пять local UDP MAVLink links для готового
MAVProxy внутри ams-gcs. Он передаёт исходные байты через BSF1, без synthetic ACK.
Сценарий и оператор выбираются существующим runner; новый orchestrator не введён.

## Геометрия и наблюдения

Канонические Town01 PLY не изменяются. Gazebo visual OBJ содержит те же вершины и
треугольники с вычисленными normals/materials. Исходные Town01 collision proxies
являются упрощёнными bounding boxes; это не точный interior mesh зданий.
Customer добавляет constrained-triangulated поле 10×10 km, высотно непрерывное
сопряжение с внешним контуром исходных поверхностей, холмы и здание с заданными
этажами. Новые visual/collision/Sionna meshes имеют единый PLY-источник.

Сцена загружается при старте. Произвольное перемещение препятствий в Gazebo,
изменение материалов, погоды или meshes во время запуска пока не обновляет RT.
Такие изменения требуют подготовки общей сцены и перезапуска. UAV не добавляются
в RT как движущиеся затеняющие объекты. НПУ и позиции излучателей статичны в
текущем контракте; их движение не поддерживается. Мощность/частота/расписание
излучателей управляются существующими native ns-3 sources. Угловая скорость
сохраняется tracker, но отдельной модели вращательного Doppler здесь нет.

MonitorSnifferRx даёт полезную мощность и combined noise/interference только
декодированных MPDU; SignalArrival даёт мощность сигнала до решения о приёме.
RxOk/RxError — decoder attempts; PhyRxEnd — нейтральное окончание сигнала.
Native queue traces наблюдают AC occupancy и время до удаления MPDU, включая
backoff/retry. Полный raw Wi-Fi capture — radiotap DLT127; Ethernet/TAP PCAP —
производное представление. Карты — offline native PSD predictions без live overhead.
Raw кадры получены с камер текущего Gazebo и связаны с odometry и временем.
